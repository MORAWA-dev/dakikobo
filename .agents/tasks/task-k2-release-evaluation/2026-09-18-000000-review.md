# Reproducible Ticket 09 release evaluation: threshold tests + offline decision scaffold (v1)

Task K2 makes the Ticket 09 release evaluation reproducible without touching agronomic behavior. It adds 15 tests to `tests/test_farmer_evaluation.py` covering the five required categories (missing evidence, duplicate identifiers, denominators, exact threshold boundaries, fail-closed release), and it adds a deterministic, fully-offline release-decision scaffold generator to `scripts/farmer_evaluation.py` (exposed as `--generate-decision`), backed by 9 tests in `tests/test_release_decision.py`. It also documents the live smoke command in `evaluation/HUMAN_VALIDATION_CHECKLIST.md` and commits one dated artifact (`RELEASE_DECISION_SCAFFOLD_2026-09-17.md`). No production agronomic code changed; the existing screening logic already enforced the numeric gates, so FEAT-002 is pure test coverage.

## High-level view

The numeric gates live entirely in `assess`, `assess_claims`, and `assess_tasks`. Claim grounding uses claim rows as the denominator and requires `rate >= .9`; pilot completion and comprehension each use participant×task observations and require `>= .8`; a single critical-safety failure short-circuits to a fail regardless of averages. The new tests pin each of these at and just below the boundary, and reverting the >=90% threshold to 80% was independently confirmed to break `test_claim_grounding_just_below_ninety_percent_fails`.

Missing evidence fails closed everywhere: empty ledgers, blank required fields, and unmarked yes/no outcomes all return `False` before any rate is computed, so no gate can report a pass without complete evidence.

The release-decision scaffold is generated offline and deterministically from repository state — commit SHA, corpus manifest hash, LLM/vision/embedding model names, and the safety-policy revision — with every human/agronomic/operational gate rendered as pending and the decision hard-coded to REPORTÉE. No reviewer, participant, result, approval, or run date is invented; human fields render as blank underscores. The live evaluation command is documented with a `<cible-autorisee>` placeholder, no embedded credentials, and an explicit statement that it was not executed.

Safety boundaries are intact: `core/fertilizer.py`, `core/source_policy.py`, `static/data/fertilizer.json`, and `Data/reviews/*` are untouched; no PR #13 P2 crop-scoped attribution is reintroduced; French user-facing wording is preserved.

### Grounding, completion, and comprehension gates

`assess_claims` computes `supported / total` over claim rows and returns `rate >= .9`; the summary states "Denominator: substantive claims reviewed." `assess_tasks` computes independent completion and next-action comprehension separately over participant×task rows and passes only when both are `>= .8`. `assess` gates the scorecard on grounding `>= .9`, success `>= .8`, and understood `>= .8`, but first short-circuits on any critical case whose `safety_pass != 'yes'` — an average cannot rescue a critical-safety failure.

The boundary tests pin the exact edges: 9/10 claims passes, 8/9 (88.9%) fails, 32/40 pilot observations passes at exactly 80%, 31/40 completion fails, and comprehension is gated independently of completion (32 complete / 31 understood still fails). `test_pilot_denominator_is_participant_times_task_observations` asserts the denominator is 40 observations across 8 participants, not 8 participants.

A local-environment hazard is easy to misdiagnose as a source bug. The committed source reads `return rate >= .9`, and `inspect.getsource` confirms it, but the executing code object in this worktree compares against `0.8`:

```
582 LOAD_CONST 16 (0.8)
584 COMPARE_OP  5 (>=)
```

The cause is a stale `scripts/__pycache__/farmer_evaluation.cpython-311.pyc` whose mtime equals the source file's mtime, so CPython's timestamp invalidation trusts it and never recompiles. Deleting the `.pyc` makes 8/10 correctly return `False` and all 49 K2 tests pass. The `.pyc` is gitignored and not part of the diff, so this is not a code defect — but any reviewer or CI runner that inherits this worktree's cache will see two spurious failures.

### Missing evidence fails closed

Empty ledgers (`assess_claims`/`assess_tasks` on a header-only file) and the blank scorecard all return `False` before any rate is computed. Blank required fields in a claim row ("Incomplete claim evidence…") and a blank `observer` in a task row ("Incomplete participant task evidence.") both fail closed, and `test_missing_evidence_never_yields_release_pass` asserts that with no evidence at all none of the three ledgers can report a pass. Duplicate identifiers are rejected in all three ledgers (duplicate case ids, duplicate `(case_id, claim_id)`, duplicate `(participant_code, task_id)`), each with an exact-message assertion.

### Deterministic offline scaffold

`generate_release_decision` renders the scaffold from explicit inputs so `release_decision_scaffold` is a pure function of `(commit, generated_on, corpus, models, policy_revision)`; `test_body_is_deterministic_for_fixed_inputs` and the two-write test confirm byte-identical output. The build identity comes from repository state: `_current_commit()` shells `git rev-parse HEAD` (falling back to a clearly-marked French placeholder if git is unavailable), `_corpus_identity()` reuses `build_source_manifest` + `manifest_hash`, and model names and `safety_policy_revision()` are read from `config`/`core.answer_safety`.

The corpus fingerprint is computed by enumerating the on-disk corpus (`list_markdown_files`/`list_pdf_files`) through `config` at generation time. That makes the hash match the running vector-store identity on the evaluated build, but it also means the recorded fingerprint is a property of the generating environment, not a pinned input captured in the scaffold call. If the intended contract is "the scaffold must be regenerated on the exact build under evaluation," this is correct; if it is "reproduce an old decision from recorded inputs," the corpus layout would need to be an explicit input like the others.

The committed artifact records commit `a41c842…` (the FEAT-003 commit, expected since it was generated before the final metadata commit), `safety-2026-09-09.1f0345c393fd`, the three model names, and a 2-document Markdown corpus with hash `11391cefa86f9f32` — consistent with `PREFER_MARKDOWN_KB` selecting the Markdown KB.

### No fabricated human data; every gate pending

Every gate section (agronomist, phone rehearsal, participant observations, live-model, hosting) renders `☐ en attente` and blank `＿＿＿` fields. The decision block hard-codes `[x] REPORTER` with `[ ] LIVRER` and `[ ] RÉDUIRE`, and all four decision-table result cells stay `À mesurer`. `test_human_fields_stay_blank_with_no_invented_data` bounds every `YYYY-MM-DD` string in the body to the injected generation date, the policy-revision date, and the one legitimate reference to a dated checklist artifact — so no reviewer, result, or approval date can be smuggled in. The REPORTÉE state is a template literal, not derived from evidence, so it cannot be flipped by the generator.

### Live command documented, not executed, no credentials

`LIVE_EVALUATION_COMMAND` targets `https://<cible-autorisee>` with `--strict`, carries no credentials, and the body states in French that it was not executed and that secrets come only from the process environment (per AGENTS.md, no `.env` loading). The tests assert `GROQ`/`API_KEY` never appear in the body and that the "n'a PAS été exécutée" disclaimer is present. The same command and the `--generate-decision` invocation are mirrored into `HUMAN_VALIDATION_CHECKLIST.md` under a new French section.

### Safety boundaries preserved

`git diff --name-only` against the base confirms `core/fertilizer.py`, `core/source_policy.py`, `static/data/fertilizer.json`, and `Data/reviews/*` are untouched; no `prosol`/reviews eligibility files appear in the diff, so PR #13's P2 crop-scoped attribution is not restored. `NUMERIC_GUIDANCE_VERIFIED` is not modified. All user-facing strings added are French.

### Silent split-mixing is enforced indirectly

`assess` classifies the row set by its split values: a pure `development` or `held_out` set is scoped to that split, the full `{development, held_out}` set is treated as the complete 60-case benchmark, and anything else returns "Scorecard must contain one complete split or the complete benchmark." A 20-dev + 20-held subset therefore matches the full-benchmark branch and is rejected by the subsequent 40≠60 count check ("Incomplete or duplicate case identifiers."), verified by direct execution. The guarantee holds, but it rides on the count check rather than an explicit anti-mixing assertion, and no new test locks this path — a refactor that loosened the count check could reintroduce silent mixing undetected.
